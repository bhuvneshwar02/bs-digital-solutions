Technical Overview & Explainer

How bsinnovationsolutions.com Was Built

BS Innovation Solutions  ·  Bhuvneshwar Sharma  ·  Full‑stack web application  ·  Prepared September 2026

This document explains, in plain language and in technical detail, how the website bsinnovationsolutions.com is built and how every part of it works. It is written so that a non‑technical reader can follow the ideas, and a technical reader (a client's IT team, a recruiter, another developer) gets the exact stack and architecture.

The one‑paragraph version. This is not a template or a WordPress site. It is a custom full‑stack web application. The part visitors see is built with React (JavaScript). The content — every heading, service, project, price and review — lives in a MongoDB database and is served by a custom Node.js / Express API. There is a password‑protected admin panel where the whole site can be edited without touching code. The site is hosted in three pieces: the visible site on Hostinger, the API on Render, and the database on MongoDB Atlas.

1   What the website is

bsinnovationsolutions.com is the online home of BS Innovation Solutions, the freelance practice of Bhuvneshwar Sharma — a freelance full‑stack web, app and AI developer based in Rampur, Uttar Pradesh, working remotely across India and worldwide.

The site is a marketing and lead‑generation website with a full content‑management system behind it. It has:

  • Public pages — Home, About, Services (17 individual service pages), Portfolio (project case studies), Pricing, Blog, Reviews, Gallery, a community Job Board, and Contact.
  • Interactive features — a contact form, two application forms (start a project / work with me), a public "leave a review" form with admin moderation, a public "post a job" board with poster‑identity verification, a floating WhatsApp button, and a floating review button.
  • A private admin panel at /admin where every word, image, price, service and review on the site is edited, and where all form submissions arrive.

In plain terms: think of it as two apps that talk to each other. One is the public website. The other is a private control room (the admin panel). The control room writes to a database; the public website reads from that same database. Change something in the control room, and it appears on the live site.

3   How the pieces fit together

┌───────────────────────────────┐ │ VISITOR'S BROWSER │ │ React app (HTML/CSS/JS) │ └───────────────┬───────────────┘ │ HTTPS request for data │ GET /api/bootstrap ▼ Hostinger Render (Node + Express API) serves the ────────────► ┌──────────────────────────┐ built React files │ Routes → Validation │ (bsinnovationsolutions.com) │ Auth (JWT) → Controllers │ └────────────┬─────────────┘ │ Mongoose queries ▼ MongoDB Atlas (the database) ┌──────────────────────────┐ │ site settings, services, │ │ projects, blog, pricing, │ │ reviews, job posts, │ │ form submissions, users │ └──────────────────────────┘

The request flow, step by step

  1. A visitor opens bsinnovationsolutions.com. Hostinger sends back index.html and the JavaScript bundle.
  2. The React app starts in the browser. It immediately calls the API once: GET /api/bootstrap.
  3. The Render API receives that call, reads all the site content from MongoDB Atlas in one go, and returns it as JSON.
  4. React renders the pages using that content. Moving between pages after that is instant — no page reloads.
  5. When a visitor submits a form, React sends the data to the API (e.g. POST /api/contact). The API validates it, saves it to the database, and emails a notification.
  6. The site owner logs into /admin, which is the same React app in a different mode. It talks to the protected /api/admin/* endpoints to edit content and read submissions.

Why split it into three services? Each piece can be hosted where it is cheapest and best: static files are free and fast on Hostinger; the API needs a real server, which Render provides; the database is a managed, backed‑up cloud service. They are joined only by web addresses and a shared secret, so any one can be moved or upgraded without rewriting the others.

The "always works" safety net

The front‑end ships with a bundled copy of the site's content built into it. If the API is ever slow or unreachable (for example, Render's free tier "sleeps" after 15 minutes of no traffic and takes ~30 seconds to wake), the site still renders instantly from that built‑in copy and then quietly refreshes with live data once the API responds. The visitor never sees a broken page.

4   The front‑end — what visitors see

It is a "single‑page application" (SPA)

The browser loads one HTML file. React then draws every page and swaps content in and out as the visitor navigates, using React Router for the URLs. This makes navigation feel instant.

Built from reusable components

The interface is assembled from small building blocks in src/components/ (Navbar, Footer, Logo, buttons, the reviews row, forms…) and page files in src/pages/ (Home, About, Services…). A component is written once and reused everywhere.

Code‑splitting for speed

Vite splits the app into ~25 small files. The browser only downloads the code for the page being viewed. The first load is roughly 130 KB compressed; the rarely‑changing parts (React itself, the animation library) are cached separately so repeat visits are near‑instant.

How content reaches the page

A single component, ContentProvider, fetches /api/bootstrap once when the app starts and makes the result available to every page through a hook called useContent(). Pages never hard‑code their text — they read it from this shared content. That is what lets the admin panel control everything.

Styling

All visual design is done with Tailwind CSS utility classes directly in the components, with a small custom theme (the navy #12172B, marigold #F2A93B and teal #17917E brand colours, and the Space Grotesk / Inter / JetBrains Mono fonts). Animations use Framer Motion.

Other front‑end details

  • Metadata per page — React 19 places the correct <title> and description tags in the page head for each route, for SEO and link previews.
  • Scroll handling — every navigation returns to the top of the page; a reload no longer restores an old scroll position.
  • The "BS" logo is drawn in code as an SVG (scalable vector), so it is crisp at any size and used everywhere including the browser‑tab icon.

5   The back‑end — the API

The back‑end is a Node.js program using the Express framework. It is a "REST API": a set of web addresses (endpoints) that return or accept JSON data. It never sends HTML — only data.

Main endpoint groups

PathAccessPurpose
/api/healthpublicA simple "I'm alive" check used by Render
/api/bootstrap, /api/site, /api/services …public, read‑onlyAll the content the public site displays
/api/contact, /api/applications, /api/job-board, /api/reviewspublic, writeReceive form submissions; rate‑limited and validated
/api/auth/login, /api/auth/me, /api/auth/change-passwordpublic / tokenAdmin login and session
/api/admin/*token requiredCreate / edit / delete all content; read every submission; manage users
/api/metrics/hitpublicIncrements the visit counter shown in the footer

The "generic CRUD" design — the clever part

Rather than writing near‑identical create/read/update/delete code for services, projects, blog posts, pricing, FAQs and so on, the back‑end has one reusable CRUD router driven by a registry (src/routes/registry.js). The registry lists each content type, its database model, and its validation rules. Adding a new content type is a few lines in the registry plus a matching form definition on the front‑end — no new endpoint code.

Plain version: the developer wrote the "edit any list of things" machinery once, then fed it a list of what kinds of things exist. Services, projects, blog posts and the rest all run through the same tested code.

Request handling pipeline

  1. Security middleware — Helmet sets protective headers; the request is checked against rate limits; suspicious database characters are stripped; duplicated parameters are collapsed.
  2. CORS check — only the real website's address is allowed to call the API from a browser.
  3. Validation — every field is checked with a Zod schema (correct type, length limits, allowed values). Bad data is rejected with a clear message before anything is saved.
  4. Authentication (admin routes only) — the request must carry a valid, unexpired login token.
  5. Controller — the actual work: read or write the database via Mongoose.
  6. Central error handler — turns any failure into a clean JSON error with the right status code; never leaks internal details.

6   The database

The database is MongoDB — a "document" database that stores records as JSON‑like objects. Mongoose defines the shape of each collection in src/models/index.js. The main collections:

CollectionHolds
SiteSettings (one document)Brand name, contact details, social links, navigation, hero text, "hire me" block, About text, footer, SEO defaults
Service, Project, BlogPostThe 17 services, portfolio case studies, and blog articles — each with its own URL slug
PricingPlan, PricingAddon, Faq, ProcessStep, Testimonial, TechItem, TimelineItem, CoreValue, GalleryItem, ServiceCategoryThe smaller content lists shown across the site
ReviewVisitor‑submitted reviews, each with a status: pending → approved / rejected
JobPostCommunity job‑board submissions with full poster identity, moderated before publishing
ContactMessage, ApplicationEvery contact enquiry and project/collaborator application
UserAdmin accounts — name, email, hashed password, role (admin or editor), lockout state
MetricThe running total of site visits

Every content record also carries an order number and a published flag, so the admin can reorder items or hide them without deleting.

Seeding

A script (npm run seed) fills a fresh database with the starting content and creates the first admin account. It is safe to re‑run: it only adds what is missing and never overwrites content that has been edited in the admin panel.

7   The admin panel / CMS

At bsinnovationsolutions.com/admin is a password‑protected control panel. It is part of the same React app, loaded only when needed. From it the owner can:

  • Edit every piece of text and every image on the public site — brand details, navigation, hero, services, projects, pricing, blog, FAQs, gallery, SEO settings.
  • Reorder or hide any item; add or remove services, projects and posts.
  • Read every contact message, project application and collaborator application.
  • Moderate reviews — approve, reject, feature, or edit — so only genuine, approved reviews appear publicly.
  • Moderate job‑board posts — verify the poster's identity before the post goes live.
  • Manage users (admin only): add editors, change roles, unlock a locked account.
  • Change their own password.

Editors can manage content; only admins can manage users, site settings and deletions. The last remaining admin cannot be demoted or deleted.

9   Search engine optimisation (SEO)

  • Per‑page titles and descriptions written around what people actually search for, leading with "Freelancer" / "Freelance developer".
  • Structured data (Schema.org / JSON‑LD) on every page: a Person (Bhuvneshwar Sharma), a ProfessionalService (the business), a WebSite, BreadcrumbList trails, BlogPosting on articles, Service on service pages, and an AggregateRating that appears once real reviews exist. The About page carries a ProfilePage so a search for the owner's name resolves to this site.
  • Local signals — service areas (Rampur, Milak, Moradabad, Bareilly, Uttar Pradesh, India) and geo meta tags.
  • Sitemap — regenerated on every build from the live database; currently ~47 URLs including every service, project and blog post.
  • robots.txt naming Googlebot and Bingbot explicitly, pointing to the sitemap.
  • Performance — sub‑second loads, which is itself a ranking factor.
  • IndexNow — a script (npm run indexnow) that instantly notifies Bing / Yandex when content changes.
  • Blog — articles targeting real buyer questions (cost of a website, hiring a freelancer, whether to use AI), which is the main long‑term organic‑traffic engine.

Note on ranking: on‑page SEO is necessary but not sufficient. A new domain also needs to be registered in Google Search Console, submitted, and earn links from other sites (LinkedIn, GitHub, Freelancer.com, directories) before it ranks for competitive terms. That is an ongoing, off‑site effort.

10   Analytics & the visit counter

Google Analytics 4 is loaded only in the production build (measurement ID G‑09RTYSGNW0). It reports a page view on every navigation, so the owner can see traffic, sources and popular pages in real time.

Separately, a lightweight visit counter lives in the database. Each browser is counted once per session via POST /api/metrics/hit; the running total is shown in the bottom‑right of the site footer.

11   Hosting & deployment

Front‑end → Hostinger

  1. On the developer's machine: npm run build. Vite regenerates the sitemap, checks code quality, and produces a dist/ folder of optimised static files with the API address baked in.
  2. The contents of dist/ (including a .htaccess file for routing and security headers) are uploaded to Hostinger's public_html/.

Back‑end → Render

Render is connected to the GitHub repository. Every push to the main branch automatically redeploys the API. Configuration (database URL, secrets, email keys) is set as environment variables in the Render dashboard. A blueprint file (render.yaml) records the setup.

Database → MongoDB Atlas

A managed cloud cluster. The API connects using a connection string kept in Render's environment variables. Atlas handles backups and availability.

Source control → GitHub

All code is in one repository (github.com/bhuvneshwar02/bsinnovationsolutions) with frontend/ and backend/ folders. Every change is a commit with a message explaining what and why.

12   How to run and change it

Run locally

cd backend   &&  npm install  &&  npm run dev     # API on http://localhost:4000
cd frontend  &&  npm install  &&  npm run dev     # site on http://localhost:5173

Common operations

TaskCommand / action
Edit site contentLog in at /admin — no code needed
Load starting content into a databasecd backend && npm run seed
Unlock a locked admin accountcd backend && npm run unlock -- <email>
Rebuild the public sitecd frontend && npm run build, then upload dist/
Notify Bing of new contentcd frontend && npm run indexnow
Deploy the APIgit push — Render redeploys automatically

Add a new page or content type

Add its model in backend/src/models/index.js, register it in backend/src/routes/registry.js with a Zod schema, add a matching form definition in frontend/src/admin/schemas.js, and (if it needs a public page) a component in frontend/src/pages/ with a route in frontend/src/App.jsx. The generic CRUD system handles the rest.
